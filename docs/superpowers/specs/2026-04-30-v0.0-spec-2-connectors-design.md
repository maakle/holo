# holo v0.0 Spec #2: First connectors + retrieval — Design

**Status:** Approved · **Date:** 2026-04-30 · **Owner:** Mathias

This is sub-project #2 of holo v0.0. v0.0 itself is a 6-week internal substrate milestone (see `docs/ROADMAP.md`). Sub-project #1 (Foundation) shipped on 2026-04-30 (`e961750`). Spec #2 builds end-to-end ingestion + retrieval on top of Foundation.

Per the brainstorming session on 2026-04-30, the scope decomposition was revisited. Foundation's spec framed spec #2 as "GitHub + `search` only," but the ROADMAP's Week 1 actually wants the full codebase+KB cluster. Spec #2's scope was expanded to match the ROADMAP: **GitHub + Slack + Notion + four MCP tools** (`search`, `get_thread`, `get_pr`, `get_doc`). Spec #3 (originally "remaining connectors") becomes "customer cluster" — Pylon + HubSpot + Grain.

---

## What this is

Spec #2 wires Foundation's GitHub OAuth scaffolding into a working substrate: ingestion pipeline, hybrid retrieval, and four MCP tools. After Spec #2 ships, the founder's three agents (support-question, interview-prep, customer-success prototype) can run on holo's MCP endpoint instead of bespoke fetchers.

It exists to prove:

- The full ingestion pipeline (clone → chunk → embed → index) works end-to-end against three platforms with very different shapes
- Hybrid retrieval (pgvector + tsvector via RRF) returns useful results across mixed providers
- The four MCP tools surface results in shapes the founder's existing agents already understand
- Allowlist enforcement is real (config-driven, audit-trailed, enforced at ingest)
- Source code retrieval works alongside prose retrieval via a per-domain embedder routing layer
- Per-source incremental sync via cursor checkpoints keeps API budgets within their hourly quotas

## Definition of done

After Spec #2 ships, on a clean machine with Foundation already running:

1. Founder runs `holo allowlist add github "kombo-tech/*"`, `holo allowlist add slack "C0123ABC,C0456DEF"`, `holo allowlist add notion "<page-tree-root-id>"` via the new CLI.
2. Each connector's "Connect" flow on `/connections` works:
   - GitHub: existing OAuth roundtrip (no change from Foundation)
   - Slack: new OAuth click-through, bot installed by org admin
   - Notion: paste internal-integration token + verify, see list of currently-shared pages
3. After connect + allowlist, the founder runs `holo sync github` (or it autostarts via the BullMQ repeatable job).
4. Within ~30 minutes for a typical 10-repo / 20-channel / 50-page setup: ~25K–60K chunks land in `chunks` table, embedded, indexed.
5. Claude Desktop config now points at holo's MCP server. The founder's existing support-question agent calls `search { q: "MFA retention" }` → gets ranked chunks across all 3 sources with proper ACL filtering. Calls `get_pr { owner, repo, number }` → returns PR title + description + linked issue + per-file diffs + review thread.
6. Background: every 6h, BullMQ refreshes each source via incremental sync (`git diff` for code, Slack `oldest` cursor for messages, Notion `last_edited_time` for pages); only changed/new artifacts get re-embedded. Chunk-level content-hash dedupe absorbs reformats and import-only changes for free.
7. The support-question agent's 3 ROADMAP parity queries (Jesse's MFA/retention, Mo's workable ID, Maria's UKG Pro) return useful results within 2s. This is the dogfood gate.
8. CI green: lint + typecheck + tests + e2e. Full-sync integration test against recorded GitHub/Slack/Notion fixtures verifies chunks land with correct shape.

## Schema migration (one Drizzle migration)

### New columns on existing tables

- `chunks.content_hash text NOT NULL` — sha256 of `kind || ':' || content`. Used for dedupe across re-syncs. Indexed.
- `chunks.embedding_model text NOT NULL DEFAULT 'openai-3-large'` — `'openai-3-large'` or `'voyage-code-3'`. Used by query-router to know which model embedded which chunks.
- `chunks.metadata jsonb` already exists; populated with per-source structured fields:
  - GitHub PR chunks: `{ pr_number, repo_full_name, kind: 'title' | 'diff' | 'review' }`
  - GitHub issue chunks: `{ issue_number, repo_full_name, kind: 'body' | 'comment' }`
  - GitHub doc chunks: `{ repo_full_name, file_path, breadcrumb }`
  - GitHub code chunks: `{ repo_full_name, commit_sha, file_path, symbol_name?, start_line, end_line, language }`
  - Slack chunks: `{ channel_id, channel_name, thread_ts, participant_user_ids, permalink }`
  - Notion chunks: `{ notion_page_id, notion_database_id?, breadcrumb, block_id?, last_edited_by_user, last_edited_time }`
- `connector_cursors.metadata jsonb DEFAULT '{}'::jsonb` — per-source state:
  - GitHub-code: `{ last_indexed_sha: '<sha>' }` per repo
  - GitHub-prose: `{ latest_pr_updated_at, latest_issue_updated_at, last_doc_walk_at }` per repo
  - Slack: `{ oldest_per_channel: { 'C0123': '1700000000.000100', ... } }`
  - Notion: `{ last_edited_per_page: { 'page_id': '2026-04-29T...' } }`

### New table: `connector_allowlists`

```sql
CREATE TABLE connector_allowlists (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id uuid NOT NULL REFERENCES organization(id),
  provider        text NOT NULL,                     -- 'github' | 'slack' | 'notion'
  pattern         text NOT NULL,                     -- 'kombo-tech/*', 'C0123ABCD', '<page_id>'
  pattern_kind    text NOT NULL,                     -- 'glob' | 'exact_id'
  decision        text NOT NULL DEFAULT 'include',   -- 'include' | 'exclude'
  created_at      timestamptz NOT NULL DEFAULT now(),
  created_by      uuid REFERENCES "user"(id),
  notes           text                               -- audit context
);

CREATE INDEX connector_allowlists_org_provider_idx
  ON connector_allowlists(organization_id, provider);
```

Allowlist resolver: at job dispatch time, the worker reads `(include patterns) MINUS (exclude patterns)` for the org+provider, materializes the resolved list, passes it into `SyncContext`. Connector implementations get the resolved list and never query the DB.

### New indexes

- `chunks_content_hash_idx` — btree on `(organization_id, content_hash)` for dedupe lookups during embedding pipeline
- `chunks_metadata_pr_idx` — GIN on `(metadata jsonb_path_ops)` so `get_pr` can fetch all chunks for a PR via `WHERE metadata @> '{"pr_number": 1234}'`. Same pattern for `get_thread`, `get_doc`.

## Chunker contract

```ts
interface Chunker<TInput> {
  readonly kind: string;                          // 'github-pr', 'slack-thread', 'github-code', etc.
  readonly embeddingModel: 'openai-3-large' | 'voyage-code-3';
  chunk(input: TInput, ctx: ChunkContext): Promise<Chunk[]>;
}

interface Chunk {
  content: string;                                // the text to be embedded
  parentExternalId?: string;                      // groups chunks of one artifact
  metadata: Record<string, unknown>;              // source-specific fields
  aclSubjects: string[];                          // who can see this (org-level for v0.0)
}

interface ChunkContext {
  organizationId: string;
  sourceId: string;
  sourceArtifactId: string;
  treeSitter?: TreeSitterRegistry;                // lazy-loaded language grammars
}
```

The ingestion worker is provider-agnostic — it pulls raw artifacts via the connector, hands them to the right chunker, then to the embedder router, then writes chunks via `packages/retrieval-core`.

## Embedder contract

```ts
interface Embedder {
  readonly model: 'openai-3-large' | 'voyage-code-3';
  readonly dimensions: 1024;
  embed(texts: string[]): Promise<number[][]>;    // batched
}
```

Both adapters batch (OpenAI: 100 at a time; Voyage: 128 at a time per their docs), retry on rate limit with exponential backoff (shared helper in `packages/connectors/shared`), and emit metrics via Pino.

## ACL subjects (per-source, v0.0)

For v0.0 single-tenant single-user, the ACL is essentially "the org" — but `acl_subjects` is populated correctly so v0.1's per-user-OAuth fan-out is a query change, not an ingestion change:

- **GitHub**: `acl_subjects = ['org:<organization_id>']`
- **Slack**: `acl_subjects = ['org:<organization_id>', 'slack-channel:<channel_id>']`
- **Notion**: `acl_subjects = ['org:<organization_id>', 'notion-page-tree:<root_id>']`

Search query ACL filter: `acl_subjects && ARRAY['org:<org_id>']` — overlap with the user's effective subject set. v0.0's set is just `['org:<org_id>']`. v0.1's set will include per-channel/page memberships.

## GitHub — code ingestion data flow

**Trigger**: BullMQ job `github-code-sync` dispatched per-repo (one job per allowlisted repo). Repeatable every 6h; manual dispatch via `holo sync github`.

**Job steps** (each wrapped by a `step()` checkpoint helper that idempotently records progress to `connector_cursors.metadata`):

1. Resolve allowlist for `provider='github'`; expand glob patterns against `GET /user/repos` (paginated, ~5K req/hr budget).
2. For each repo: read `last_indexed_sha` from cursor. If null → full initial sync; else → incremental.
3. **Initial sync:** `git clone --depth=1 https://x-access-token:${decrypted_token}@github.com/${owner}/${repo}.git` to a worker temp dir (e.g., `/tmp/holo-clone-${job_id}`).
4. **Incremental sync:** `cd <existing-clone> && git fetch --depth=1 origin && git diff --name-status ${last_sha} HEAD` to get the changed-file list.
5. Walk file list (initial: `git ls-files`; incremental: diff list). Apply skip rules (below).
6. For each survivor: tree-sitter parse → AST chunks (~1200 tokens, 150 overlap, never split mid-function, recursive descent for oversized symbols, character-split fallback for unsupported languages).
7. Compute `content_hash` per chunk. SELECT existing hashes via `WHERE organization_id = $1 AND content_hash = ANY($2)`. Skip already-embedded.
8. Embed remainder via `voyage-code-3` (batched 128/call). Insert `chunks` rows.
9. UPSERT `connector_cursors` with new `last_indexed_sha = HEAD`.
10. Delete the worker temp dir. Disk profile: 50–500MB transient per repo; concurrency=1 for v0.0.

**Source artifact handling for code:** every code chunk has `source_artifact_id` pointing at a synthetic `source_artifacts` row per file (kind=`'github-file'`, payload=`{file_path, commit_sha, language}`). When retrieval surfaces a code chunk and the agent calls `get_doc { github_path, repo }`, the user gets the full file rebuilt by reassembling its chunks in line order.

### Skip rules

- Honor `.gitignore` via `git ls-files` (no extra parser needed)
- Hard-deny directories: `node_modules/`, `vendor/`, `dist/`, `build/`, `.next/`, `out/`, `target/`, `.venv/`, `venv/`, `__pycache__/`, `.git/`, `.cache/`, `coverage/`
- Hard-deny patterns: `*.min.{js,css}`, `*.map`, `*-lock.json`, `*.lock`, `Cargo.lock`, `pnpm-lock.yaml`, `yarn.lock`, `Pipfile.lock`, `poetry.lock`, `*.pb.{go,ts}`, `*_pb2.py`, `*.generated.*`
- Size cutoff: 512KB max, 16 bytes min
- Binary check: NUL byte in first 8KB → reject (Git's heuristic; ~99% accurate)
- Extension allow-list (not deny-list): `.ts .tsx .js .jsx .py .go .rs .java .kt .swift .rb .php .c .cc .cpp .h .hpp .cs .scala .clj .ex .exs .erl .lua .sh .sql .yaml .yml .toml .md .mdx .proto .graphql .css .scss .html .vue .svelte` — anything outside is skipped (CocoIndex pattern, safer than denylist drift).

## GitHub — prose ingestion data flow

**Trigger**: BullMQ job `github-prose-sync`, dispatched per-repo, repeatable every 6h.

**Job steps:**

1. Resolve allowlist, get repo list.
2. For each repo, fetch via Octokit:
   - **PRs**: `GET /repos/{owner}/{repo}/pulls?state=all&per_page=100&since=<cursor>` → for each PR: title, body, linked issue (parsed from `Fixes #N` / `Closes #N` in body), per-file diff (`/files`), review threads (`/reviews/{id}/comments`).
   - **Issues**: `GET /repos/{owner}/{repo}/issues?since=<cursor>&filter=all` → body + comments. Filter out PR-style issues (Octokit returns both).
   - **README + docs**: `GET /repos/{owner}/{repo}/contents/README.md` + recursive walk of `docs/` directory at HEAD, only `*.md` and `*.mdx`.
3. For each PR: `github-pr` chunker → 3 chunks (title+desc+linked-issue / per-file-diff aggregated / review-threads aggregated). For each issue: `github-issue` chunker → 1 + N chunks (body + per-comment). For each doc: `github-doc` chunker → recursive-character split with breadcrumb (`<repo> / docs / <relative_path>: <heading>`).
4. Content-hash dedupe + embed via `text-embedding-3-large` (OpenAI).
5. Cursor updates: `connector_cursors.metadata` tracks `latest_pr_updated_at`, `latest_issue_updated_at`, `last_doc_walk_at` per repo.

**Artifact reassembly**: every PR's 3 chunks share `metadata.pr_number` → `get_pr { owner, repo, number }` reassembles them. Issues group by `metadata.issue_number` → `get_doc` works for issues. README/docs group by `metadata.file_path` → `get_doc` works for docs.

## Slack ingestion data flow

**Trigger**: BullMQ job `slack-sync`, repeatable every 6h.

**Job steps:**

1. Resolve allowlist (channel IDs).
2. For each channel: `conversations.history(oldest=<cursor.oldest_per_channel[ch]>)` → returns top-level messages.
3. For each top-level message with `thread_ts`: `conversations.replies(channel, ts)` → all thread replies.
4. **Skip filters**: bot messages from CI/automation accounts (Slack's `bot_id` set, plus a curated list of automation usernames — `github`, `pagerduty`, `circleci`, `linear`); messages from users with `is_bot=true`.
5. `slack-thread` chunker: each thread becomes ONE chunk per ARCHITECTURE — concatenated as `<parent message>\n\n<reply 1>\n\n<reply 2>\n\n...` with author + timestamp prefixes (`@<user_real_name> [<HH:MM>]: <text>`). Top-level messages without a thread become their own single-message "thread" chunk.
6. Content-hash dedupe + embed via OpenAI.
7. `metadata` stores `channel_id`, `channel_name` (for display), `thread_ts`, `participant_user_ids[]`, `permalink`. Enables `get_thread { channel, ts }`.
8. Cursor update: `oldest_per_channel[ch] = max_ts_seen + 0.000001`.

**Channel rename quirk**: if a channel ID is on the allowlist but the channel was renamed since last sync, refresh `channel_name` in the resolver before storing in chunks.

## Notion ingestion data flow

**Trigger**: BullMQ job `notion-sync`, repeatable every 6h.

**Job steps:**

1. Resolve allowlist (page IDs and database IDs explicitly shared with the integration AND on the allowlist — both must be true).
2. For each allowlisted page-tree root: `pages.retrieve` + `blocks.children.list` recursive walk. For each allowlisted database: `databases.query` → list of pages → per-page block walk.
3. **Skip filters**: archived pages (`archived: true`), template pages (configurable boolean per database, default include), comment blocks (deferred to v0.1).
4. `notion-page` chunker: for each page, build a breadcrumb (`<workspace> / <ancestor1> / <ancestor2> / ...`). Generate **two flavors** of chunks:
   - **Block-level**: each top-level block (paragraph, heading, list, code block, table) becomes one chunk, with breadcrumb prepended. ~50–500 tokens per chunk depending on block size. `metadata.kind = 'block'`.
   - **Page-level summary**: for any page > 3 blocks, also emit one whole-page chunk (concatenated blocks, breadcrumb prepended). `metadata.kind = 'page'`. Caps at ~3000 tokens; longer pages truncated with `[truncated]` marker.
5. Content-hash dedupe + embed via OpenAI.
6. `metadata` stores `notion_page_id`, `notion_database_id?`, `breadcrumb`, `block_id?`, `last_edited_by_user`, `last_edited_time`. Enables `get_doc { notion_page_id }` to reassemble page chunks in order.
7. Cursor update: `last_edited_per_page[page_id] = last_edited_time` — Notion's rate limits (3 req/sec sustained) mean we incrementally pick up only changed pages.

**Notion rate-limit handling**: `@notionhq/client` SDK auto-handles 429 with `Retry-After`; our shared backoff helper wraps around it with circuit-breaker semantics (3 consecutive 429s → pause queue for 60s).

## Hybrid retrieval

`packages/retrieval-core/search.ts` exposes one function:

```ts
search(input: {
  organizationId: string;
  q: string;
  topK?: number;                      // default 10
  provider?: 'github' | 'slack' | 'notion';
  userSubjects?: string[];            // default ['org:<organizationId>']
}): Promise<SearchResult[]>;
```

Implementation: single SQL CTE composing pgvector + tsvector + ACL filter + Reciprocal Rank Fusion:

```sql
WITH
  query_vec AS (SELECT $query_embedding::vector(1024) AS v),
  vector_ranked AS (
    SELECT id, ROW_NUMBER() OVER (ORDER BY embedding <=> (SELECT v FROM query_vec)) AS rank
    FROM chunks
    WHERE organization_id = $org_id
      AND embedding_model = $query_model
      AND acl_subjects && $user_subjects
      AND ($provider IS NULL OR provider = $provider)
    ORDER BY embedding <=> (SELECT v FROM query_vec)
    LIMIT 100
  ),
  bm25_ranked AS (
    SELECT id, ROW_NUMBER() OVER (
      ORDER BY ts_rank(content_tsvector, plainto_tsquery('english', $query_text)) DESC
    ) AS rank
    FROM chunks
    WHERE organization_id = $org_id
      AND content_tsvector @@ plainto_tsquery('english', $query_text)
      AND acl_subjects && $user_subjects
      AND ($provider IS NULL OR provider = $provider)
    ORDER BY ts_rank(content_tsvector, plainto_tsquery('english', $query_text)) DESC
    LIMIT 100
  ),
  fused AS (
    SELECT id, SUM(1.0 / (60 + rank)) AS rrf_score
    FROM (
      SELECT id, rank FROM vector_ranked
      UNION ALL
      SELECT id, rank FROM bm25_ranked
    ) t
    GROUP BY id
    ORDER BY rrf_score DESC
    LIMIT $top_k
  )
SELECT c.* FROM fused f JOIN chunks c ON c.id = f.id ORDER BY f.rrf_score DESC;
```

RRF constant `k=60` is the original paper's recommendation; vector top-100 + BM25 top-100 → fused top-K.

`query_model` selects which embedding-model bucket to search. The query-router (`packages/retrieval-core/query-router.ts`) decides which based on heuristics: query contains `class `, `function `, `def `, `import `, code-like patterns → voyage; otherwise → openai. v0.0 emits a SECOND query with the other model when the first returns < 5 results, merges via RRF too.

## MCP tool surface

`apps/mcp` mounts `POST /mcp` with the JSON-RPC envelope. Four tool handlers, each guarded by the cookie+DB session middleware (Foundation's existing layer). Tool schemas in Zod, surfaced via MCP's `tools/list` so Claude Desktop / Cursor / Cline can discover them:

### `search`

```ts
search({ q: string, top_k?: number = 10, provider?: 'github'|'slack'|'notion' })
  → { results: Array<{
      chunk_id: string;
      content: string;
      score: number;
      source: { provider: string; artifact_kind: string; metadata: object };
      snippet_url?: string;          // GitHub PR URL, Slack permalink, Notion page URL
    }> }
```

### `get_pr`

```ts
get_pr({ owner: string, repo: string, number: number })
  → { title, body, linked_issue?, files: Array<{path, diff_excerpt}>,
      reviews: Array<{author, body, comments}> }
```

Reassembles the 3 chunks. Throws `HOLO_ARTIFACT_NOT_FOUND` if not ingested.

### `get_thread`

```ts
get_thread({ channel: string, ts: string })
  → { channel_name, parent: {author, ts, text},
      replies: Array<{author, ts, text}>, permalink }
```

Single chunk with structured reassembly.

### `get_doc`

```ts
get_doc({ artifact_id: string }
       | { notion_page_id: string }
       | { github_path: string, repo: string })
  → { kind, breadcrumb?, content, metadata }
```

Discriminated union of identifier shapes.

All four respond in standard MCP shape with `content: [{ type: 'text', text: <JSON-stringified result> }]` and surface `HoloError` codes via JSON-RPC error envelope.

## Job topology (BullMQ)

Five queues, one repeatable job per (org × provider × resource):

| Queue | Concurrency | Repeat | Per-job scope |
|---|---|---|---|
| `github-code-sync` | 1 | 6h | one repo |
| `github-prose-sync` | 3 | 6h | one repo |
| `slack-sync` | 3 | 6h | one workspace |
| `notion-sync` | 2 | 6h | one workspace |
| `embed` | 5 | n/a | a batch of chunks needing embedding |

Code-sync concurrency=1 because of disk pressure (clones). Prose-sync concurrency=3 because Octokit batches share a 5000/hr token-pool. Slack at 3 against the per-token rate-limit. Notion at 2 because of its 3 req/sec ceiling. Embed at 5 because both OpenAI and Voyage tolerate parallel batches.

`step()` checkpoint helper writes intermediate state to `connector_cursors.metadata` after each step (e.g., "completed cloning, about to walk files") — on worker crash mid-job, the job retries from the last checkpoint instead of from scratch.

## Error handling

Six new HoloError codes (extending Foundation's set):

| Code | When |
|---|---|
| `HOLO_ALLOWLIST_EMPTY` | Sync triggered but org has no include-patterns for that provider |
| `HOLO_ALLOWLIST_OVERSIZED` | Allowlist write would resolve to > 50 repos / channels / pages |
| `HOLO_INGESTION_RATE_LIMITED` | Upstream API (GitHub / Slack / Notion / OpenAI / Voyage) returned 429 after retries exhausted |
| `HOLO_CLONE_FAILED` | git clone exited non-zero or worker disk pressure |
| `HOLO_CHUNKER_FAILED` | tree-sitter parse error / unsupported language with no fallback |
| `HOLO_ARTIFACT_NOT_FOUND` | `get_*` MCP tool called with ID not in `chunks`/`source_artifacts` |

All flow through the existing `HoloErrorFilter` (apps/api) and the Hono onError handler (apps/mcp), serialized with `code/problem/cause/fix/docs_url`.

## Testing strategy

| Layer | What gets tested |
|---|---|
| Unit | Each chunker tested with a fixture artifact, snapshot-tested chunk count + content. Embedder router routes `kind:'github-code'` → voyage, everything else → openai. Allowlist resolver glob expansion. Skip-rules helpers (binary detect, size cap, extension allow). |

## Estimated effort

**Roughly 8–12 days** of focused work for an experienced engineer:

- GitHub code ingestion (clone + tree-sitter + voyage embedding pipeline + skip rules + diff incremental): ~3 days
- GitHub prose ingestion (PRs + issues + README/docs via Octokit, 3-chunk PR shape, OpenAI embedding): ~1.5 days
- Slack connector (Bolt SDK, channel allowlist, thread chunker, OpenAI embedding): ~1.5 days
- Notion connector (notion-sdk, integration token verify UI, page-tree allowlist, hybrid block+page chunker, OpenAI embedding): ~1.5 days
- `packages/retrieval-core` filling in: hybrid SQL CTE (pgvector + tsvector RRF fusion), ACL filtering, query-time embedding routing: ~1.5 days
- 4 MCP tools (`search`, `get_thread`, `get_pr`, `get_doc`) with Zod request/response schemas + JSON-RPC handler in `apps/mcp`: ~1 day
- BullMQ job topology (per-source queues, `step()` checkpoint helper, content-hash dedupe): ~1 day
- Allowlist DB migration + CLI (`holo allowlist add/list/remove`) + per-connector resolution: ~0.5 day
- Tests + fixtures + parity smoke against the 3 ROADMAP queries: ~1.5 days
- 8–12d total range covers chunker tuning variance and unknowns at platform boundaries (Notion's API surfaces are notoriously quirky, Slack thread pagination has edge cases).

If anything runs long, the right thing to cut is **GitHub source code ingestion** (largest single piece, defer to spec #2.1). The prose surfaces + 3 prose tools are the must-ship for the agent migration. v0.0 dogfood gate at week 6 doesn't require code-search to pass.

## Risks and how we'll know

| Risk | Mitigation | Detection |
|---|---|---|
| Voyage outage stalls code ingestion | Code chunks fall back to tsvector BM25 (already in place); retrieval still works without semantic match | Pino metrics on Voyage 5xx / 429 rate; alert at >5% over 1h |
| Disk pressure from concurrent code clones | BullMQ concurrency=1 for `github-code-sync`; cleanup on job complete + on worker shutdown | Worker exit on disk full; shutdown hook removes temp dirs |
| Allowlist drift catches wrong repo | Cap of 50 resolved repos/channels/pages per allowlist write; warning logged when an allowlist write exceeds 25 | `HOLO_ALLOWLIST_OVERSIZED` thrown at write time |
| Slack/Notion token revoked mid-sync | Connector returns 401; cursor not advanced; status flipped to `revoked` in `connector_credentials`; UI surfaces "Reconnect" CTA | Health-check sync run nightly |
| Retrieval quality below dogfood gate | Build agents against `search` first, run 3 ROADMAP queries, measure parity vs bespoke fetcher; if parity fails, contextual chunking is the first lever | Parity smoke test in CI |
| Notion page hierarchy changes mid-sync (page moved/deleted) | Cursor strategy is per-page `last_edited_time`; deleted pages just stop appearing in subsequent walks; we don't aggressively delete chunks (acceptable staleness for v0.0) | Manual reconciliation in v0.1 if it becomes a problem |
| tree-sitter grammar missing for a language we encounter | Character-split fallback; logged as `HOLO_CHUNKER_FALLBACK` warning | Grammar coverage tracked per repo in metrics |
