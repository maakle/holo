**Phases covered:** Phase 9 (BullMQ queue topology + `step()` checkpoint helper + per-connector worker wiring + embed queue), Phase 10 (retrieval-core: hybrid SQL CTE, query router, get-artifact reassembly).

**Why these phases:** Phase 9 turns the connector functions from Parts 3-4 into resumable jobs — `step()` checkpoint resume is what makes 30-minute syncs survive worker restarts. Phase 10 is the retrieval brain — one SQL CTE that fuses pgvector + tsvector via Reciprocal Rank Fusion, plus a query router that decides whether to embed with OpenAI or Voyage. Get the SQL wrong and retrieval quality collapses; get the router wrong and code searches lose semantic match.

## Verbatim SQL — must be reproduced exactly in Task 10.1

```sql
WITH
  query_vec AS (SELECT $query_embedding::vector(1024) AS v),
  vector_ranked AS (
    SELECT id, ROW_NUMBER() OVER (ORDER BY embedding <=> (SELECT v FROM query_vec)) AS rank
    FROM chunks
    WHERE organization_id = $org_id
      AND embedding_model = $query_model
      AND acl_subjects && $user_subjects
      AND ($provider IS NULL OR provider = $provider)
    ORDER BY embedding <=> (SELECT v FROM query_vec)
    LIMIT 100
  ),
  bm25_ranked AS (
    SELECT id, ROW_NUMBER() OVER (
      ORDER BY ts_rank(content_tsvector, plainto_tsquery('english', $query_text)) DESC
    ) AS rank
    FROM chunks
    WHERE organization_id = $org_id
      AND content_tsvector @@ plainto_tsquery('english', $query_text)
      AND acl_subjects && $user_subjects
      AND ($provider IS NULL OR provider = $provider)
    ORDER BY ts_rank(content_tsvector, plainto_tsquery('english', $query_text)) DESC
    LIMIT 100
  ),
  fused AS (
    SELECT id, SUM(1.0 / (60 + rank)) AS rrf_score
    FROM (
      SELECT id, rank FROM vector_ranked
      UNION ALL
      SELECT id, rank FROM bm25_ranked
    ) t
    GROUP BY id
    ORDER BY rrf_score DESC
    LIMIT $top_k
  )
SELECT c.* FROM fused f JOIN chunks c ON c.id = f.id ORDER BY f.rrf_score DESC;
```

## Phase 9 — BullMQ queues + workers (3 tasks)

- **Task 9.1:** `step()` checkpoint helper at `apps/worker/src/step.ts`. Function `step<T>({ jobId, name, run }: { jobId: string; name: string; run: () => Promise<T> }) → Promise<T>` — checks `connector_cursors.metadata.checkpoints.<jobId>.<name>` for existing result; if present, returns it (skip re-execution); else runs, persists `{ name, result, completedAt }` into the cursor's metadata via JSONB `jsonb_set` update, returns. The cursor row is keyed by `(sourceId, scope='checkpoints')` — a dedicated scope per source so checkpoint state never collides with sync cursors. Persistence MUST be a single UPDATE statement so a worker crash mid-write can't corrupt half a checkpoint. Test: vitest with in-memory pg shim → assert idempotency on re-run after partial completion: enqueue a fake job that runs three named steps, kill it after step 2 completes, restart → assert step 1 + 2 are skipped (returns cached values), step 3 runs.

- **Task 9.2:** Per-connector queue + worker wiring under `apps/worker/src/queues/`. Create four files (`github-code.ts`, `github-prose.ts`, `slack.ts`, `notion.ts`), each instantiating a BullMQ `Queue` + `Worker` pair with concurrency from the topology table: `github-code-sync` (1), `github-prose-sync` (3), `slack-sync` (3), `notion-sync` (2). All four register a repeating job per source-id via `queue.add(name, payload, { repeat: { every: 6 * 60 * 60 * 1000 } })` — repeat-every is 6h. Worker handlers dispatch by cursor presence: read `connector_cursors` for the `(sourceId, scope='sync')` row → if absent, call the connector's `fullSync` (Slack / Notion / GitHub-prose); if present, call `incrementalSync`. For the `github-code-sync` queue the dispatch instead branches on `connector_cursors.metadata.last_indexed_sha` — null ⇒ `sync-code-initial`, non-null ⇒ `sync-code-incremental` (both functions defined in Part 4 Phase 8). Wrap every connector call in `step({ jobId: job.id, name: 'connector-sync', run: () => connector.fullSync(...) })` so a partial sync resumes on retry. Wire all four queue modules' registration calls into `apps/worker/src/app.module.ts` `OnModuleInit`. Test: integration test with a real ioredis-mock that enqueues one Slack sync job, mocks `createSlackConnector()` to return a stub, asserts the worker invokes `fullSync` exactly once and that the cursor row gets written.

- **Task 9.3:** `embed` queue + worker at `apps/worker/src/queues/embed.ts`. Concurrency=5, no `repeat` (jobs are one-shot, enqueued by the connector workers). Job payload shape:
  ```ts
  type EmbedJobPayload = {
    chunks: ChunkInsertPayload[];      // shape from Part 2 chunkers
    organizationId: string;
    sourceArtifactId: string;
  };
  ```
  Worker pseudocode: (1) group `payload.chunks` by `embeddingModel` (`'openai-3-large'` for prose, `'voyage-code-3'` for code); (2) for each group call `embedChunks` from Part 1 Task 2.4 → `{ chunk, embedding }[]`; (3) bulk INSERT into `chunks` with `embedding`, `content_hash`, `embedding_model`, plus all chunker-supplied metadata (`provider`, `artifact_kind`, `acl_subjects`, `source_artifact_id`, `metadata` JSONB, etc.). Use `INSERT ... ON CONFLICT (content_hash, organization_id) DO NOTHING` so re-embedding the same chunk after a checkpoint replay is a no-op. **Connector sync functions from Parts 3-4 currently INSERT directly** — modify them in this task to instead enqueue `embed` jobs with batches of ≤50 unembedded chunks each via `embedQueue.add('embed', payload)`. Connectors no longer touch `chunks` directly except for content-hash dedup queries (still allowed). Test: enqueue a single embed job carrying 75 chunks split 50 prose + 25 code → assert 2 batches dispatched to the embedder router (one per model), 75 rows inserted with the expected `embedding_model` distribution, and a re-enqueue of the same payload produces 0 additional rows.

## Phase 10 — Retrieval-core (3 tasks)

- **Task 10.1:** Hybrid SQL CTE search at `packages/retrieval-core/src/search.ts`. Function signature:
  ```ts
  export async function search(input: {
    organizationId: string;
    q: string;
    topK?: number;        // default 10
    provider?: 'github' | 'slack' | 'notion';
    userSubjects?: string[];  // default ['org:'+organizationId]
  }): Promise<SearchResult[]>;

  export type SearchResult = {
    chunkId: string;
    content: string;
    score: number;
    source: { provider: string; artifactKind: string; metadata: Record<string, unknown> };
    snippetUrl?: string;
  };
  ```
  Implementation: (a) call `embedQuery(q)` from Task 10.2 → `{ embedding, model }`; (b) execute the verbatim SQL CTE (reproduced exactly from the block above — do NOT rewrite the CTE structure, do NOT change RRF constant `60`, do NOT change `LIMIT 100` per branch) with parameters `$org_id=organizationId`, `$query_embedding=embedding`, `$query_text=q`, `$query_model=model`, `$user_subjects=userSubjects ?? ['org:'+organizationId]`, `$provider=provider ?? null`, `$top_k=topK ?? 10`; (c) map result rows to `SearchResult[]`: `chunkId=c.id`, `content=c.content`, `score=fused.rrf_score` (re-select via the join), `source={ provider: c.provider, artifactKind: c.artifact_kind, metadata: c.metadata }`, `snippetUrl=c.metadata.url ?? c.metadata.permalink ?? undefined`. Use parametrised `$1..$N` placeholders via `pg` — never string-concat. Test: seed 5 chunks across providers (`github`, `slack`, `notion`) with mixed `acl_subjects` and a query about "MFA" — assert top-3 ordering matches the chunks containing the literal token "MFA" near top of `content`; assert that a chunk whose `acl_subjects` does NOT overlap with `userSubjects` is filtered out (not in result set); assert that `provider: 'slack'` filter excludes github + notion rows.

- **Task 10.2:** Query router + dual-model fallback at `packages/retrieval-core/src/query-router.ts`. Export:
  ```ts
  export async function embedQuery(q: string): Promise<{
    embedding: number[];
    model: 'openai-3-large' | 'voyage-code-3';
  }>;
  ```
  Heuristic: if `q` matches `/\b(class|function|def|import|from|return|interface)\b/` OR matches `/[(){};=].{3,}/` (looks code-like) → call embedder router with `{ provider: 'voyage', model: 'voyage-code-3', inputs: [q] }` and return `model: 'voyage-code-3'`; else call `{ provider: 'openai', model: 'text-embedding-3-large' }` and return `model: 'openai-3-large'`. **Dual-model fallback lives in `search.ts`, not here:** if the first SQL CTE returns < 5 results, `search.ts` calls `embedQuery` again forcing the OTHER model (export an internal `embedQueryWith(q, model)` helper to support this), runs the SQL CTE a second time with the alternate `$query_model`, then RRF-fuses the two `SearchResult[]` sets in JS using the same constant `k=60` formula (`score = sum(1 / (60 + rank_in_each_set))`), returns top-K. Test cases: (a) `'how do I reset my password?'` → openai; (b) `'function getUser(id) { return db.find(id); }'` → voyage; (c) seed only 2 chunks matching a code query under voyage but 8 chunks under openai → assert second-model invocation fired and final result set is the merged top-K with both models' chunks present.

- **Task 10.3:** `get-artifact.ts` at `packages/retrieval-core/src/get-artifact.ts`. Export:
  ```ts
  export async function getArtifact(input: {
    artifactId: string;
    organizationId: string;
  }): Promise<{ chunks: ChunkRow[]; ordered: ChunkRow[] }>;
  ```
  Implementation: SELECT all chunks WHERE `source_artifact_id = $1 AND organization_id = $2`. If empty, throw `HOLO_ARTIFACT_NOT_FOUND` (use the project's existing error code shape). Order the `ordered` array using artifact-kind-specific rules:
  - **GitHub PR** (`artifact_kind = 'pr'`): order by chunk `kind` field in metadata: `'title'` → `'diff'` → `'review'`; within each kind, order by `metadata.position ?? 0`.
  - **Doc** (`artifact_kind = 'doc'` for GitHub README/docs and Notion-doc-equivalent): order by `metadata.chunk_index` ascending (set by the chunker in Part 2).
  - **Thread** (`artifact_kind = 'thread'` for Slack): typically a single chunk; if multiple, order by `metadata.ts` ascending.
  - **Notion page** (`artifact_kind = 'notion-page'`): chunk with `metadata.kind = 'page'` first if present, then remaining chunks ordered by `metadata.block_id` lexicographically.

  Return `{ chunks: <unsorted as fetched>, ordered: <sorted per above> }` so callers can pick. This function is the load-bearing dependency for all 4 MCP tools in Part 6 (`search`, `get-artifact`, `list-sources`, `coverage`). Test: seed an artifact with 3 PR chunks (`title`, `diff`, `review`) inserted in the WRONG order → assert `ordered` array returns them as `title, diff, review`. Also seed a doc with 4 chunks at indices `[2, 0, 3, 1]` → assert `ordered` is `[0, 1, 2, 3]`. Assert `HOLO_ARTIFACT_NOT_FOUND` thrown for an unknown id.
